## 1. 目的（Why）
- Web 初心者でエンジニアを目指す人向けに、学習しやすい技術ブログを提供するための WordPress サイトを構築する。
- オリジナルテーマと、開発しやすいローカル環境（wp-env + Docker + Node + Gulp + Sass）を整備し、拡張・保守しやすい構成にする。

---

## 2. 対象ユーザー（Who）
- 主なユーザー:
  - Web 初心者〜初級レベルのエンジニア志望者
  - 技術ブログの管理者（サイトオーナー / 投稿者）
- 利用シーン:
  - 一般ユーザー: PC・スマートフォンのブラウザからブログ記事を閲覧・検索
  - 管理者: PC から WordPress 管理画面へログインし、記事投稿・編集・問い合わせ確認を行う

## 3. スコープ（What）

### 3.1 MVP 実装対象機能

#### 機能A：オリジナル WordPress テーマの作成・適用
- 何ができるか:
  - 本技術ブログ用のオリジナルテーマを作成し、WordPress サイトに適用する。
- 入出力（最低限）:
  - 入力:
    - テーマのテンプレートファイル（PHP, HTML）
    - Sass(SCSS) ファイル
    - テーマ設定（functions.php からの各種設定ファイル）
  - 出力:
    - テーマとして有効化可能な WordPress テーマ一式
    - ブラウザでのブログページ表示
- API との関係:
  - 詳細は api.md に書く（未作成）
- 受け入れ条件（必須）:
  - 前提:
    - wp-env + Docker 環境で WordPress が起動している
    - 作成したテーマが wp-content/themes 配下に配置されている
  - 操作:
    - 管理画面「外観 > テーマ」から本テーマを有効化する
  - 結果:
    - トップページ / 単一記事ページ / アーカイブページが本テーマデザインで表示される
    - レイアウトが PC / スマホで崩れず確認できる（レスポンシブの最低限対応）

#### 機能B：Sass（SCSS）+ Gulp によるスタイル管理 & ホットリロード
- 何ができるか:
  - Sass(SCSS) を Gulp でコンパイルし、ブラウザの自動リロード（ホットリロード相当）を行う。
- 入出力（最低限）:
  - 入力:
    - SCSS ファイル（テーマのスタイルソース）
    - Gulpfile（Gulp 4.0.2 設定）
  - 出力:
    - コンパイル済み CSS ファイル（テーマに読み込まれる）
    - ソース変更時のブラウザ自動リロード
- API との関係:
  - なし
- 受け入れ条件（必須）:
  - 前提:
    - Docker / Node.js v18.20.8 / NVM 環境が準備済み
    - npm で依存パッケージがインストールされている
  - 操作:
    - `npm run start` を実行し、wp-env と Gulp を起動
    - SCSS ファイルを編集・保存
  - 結果:
    - SCSS 変更が自動で CSS にコンパイルされる
    - ブラウザが自動リロードされ、スタイル変更が即時反映される（BrowserSync: http://localhost:3000）

#### 機能C：functions.php の分割構成（include フォルダ運用）
- 何ができるか:
  - functions.php から include フォルダ配下のファイル（hooks.php, setup.php, enqueue.php など）を読み込み、機能を分割管理する。
- 入出力（最低限）:
  - 入力:
    - /themes/sample-wordpress/functions.php
    - /themes/sample-wordpress/includes/hooks.php
    - /themes/sample-wordpress/includes/setup.php
    - /themes/sample-wordpress/includes/enqueue.php など
  - 出力:
    - WordPress テーマの機能（テーマサポート、フック、スクリプト・スタイルの enqueue）が分割ファイルから適用される
- API との関係:
  - なし（WordPress コアのフック・API の利用のみ）
- 受け入れ条件（必須）:
  - 前提:
    - テーマが有効化された状態
    - includes ディレクトリがテーマ内に存在
  - 操作:
    - includes 配下のファイルに機能（例：add_action, add_theme_support, wp_enqueue_scripts など）を追記
    - ブラウザでテーマを表示
  - 結果:
    - 追記した機能がエラーなく動作し、テーマ機能が期待通りに反映される
    - functions.php は分割読み込みの起点としてシンプルな構成になっている

#### 機能D：問い合わせフォーム（Contact Form 7）実装
- 何ができるか:
  - Contact Form 7 プラグインを用いて問い合わせフォームを設置し、管理者が問い合わせ内容をメールで受け取れるようにする。
- 入出力（最低限）:
  - 入力:
    - フォーム入力値（名前、メールアドレス、本文など最小限の項目）
    - フォームのショートコード（埋め込み用）
  - 出力:
    - 管理者宛の問い合わせメール送信
    - ユーザー向けの送信完了メッセージ表示
- API との関係:
  - 詳細は api.md に書く（未作成）
- 受け入れ条件（必須）:
  - 前提:
    - Contact Form 7 プラグインがインストール・有効化済み（.wp-env.json で自動インストール設定済み）
    - 固定ページまたは標準テンプレートで問い合わせページを作成
  - 操作:
    - 管理画面でフォームを作成し、ショートコードを問い合わせ用固定ページに埋め込む
    - フロント側からフォームに必要項目を入力・送信する
  - 結果:
    - バリデーションエラー時はエラーメッセージが表示され送信されない
    - 正常時は送信完了メッセージが表示され、管理者宛にメールが届く（メール送信テストで確認）
  - 備考:
    - MVP では専用テンプレート（page-contact.php）は未作成、標準の固定ページ表示を使用

#### 機能E：技術ブログとしての基本ページ構成
- 何ができるか:
  - 技術ブログとして必要な基本ページ（トップ、記事一覧、記事詳細、固定ページ（プロフィール、問い合わせなど））を表示できる。
- 入出力（最低限）:
  - 入力:
    - 管理画面から投稿・固定ページとして作成されたコンテンツ
  - 出力:
    - 一般ユーザー向けの各ページ表示
- API との関係:
  - なし（WordPress 標準機能）
- 受け入れ条件（必須）:
  - 前提:
    - テーマが有効
    - 最低限のダミー記事・固定ページが作成されている
  - 操作:
    - トップページアクセス（front-page.php が表示される）
    - 記事一覧・記事詳細ページの閲覧（現在は index.php がフォールバックとして機能）
    - プロフィールページ / 問い合わせページへの遷移
  - 結果:
    - 各ページが 404 にならず表示される
    - 記事タイトル・本文・投稿日が正しく表示される
    - グローバルナビ or フッターから基本ページに遷移できる
  - 備考:
    - MVP では single.php / archive.php / page.php は未作成、index.php がフォールバックとして機能

### 3.2 将来実装する機能（MVP では実装しない）

### 3.3 実装しないこと
- 多言語対応
- 権限管理（標準の WordPress 権限以上の細かいロール設計）
- メール / Push 通知（Contact Form 7 経由のメール送信以外）
- 外部決済連携
- 複雑な会員制機能（ログインユーザー限定コンテンツなど）

## 4. 非機能要件（最低限）

### 4.1 使用する技術（決まっていなければ未決定と書く）
- フロントエンド:
  - WordPress テーマ（PHP / HTML / Sass(SCSS) / JavaScript）
- バックエンド:
  - WordPress 6.5.5-ja（.wp-env.json で管理、日本語版）
  - PHP 8.1（.wp-env.json で指定）
- データベース:
  - wp-env が利用するデフォルト DB（MySQL/MariaDB）
- 開発環境:
  - Docker
  - wp-env（ローカル WordPress コンテナ環境）
  - Node.js v18.20.8（NVM によるバージョン管理）
  - Gulp v4.0.2
  - Sass(SCSS)
- インフラ構成管理:
  - 可能であればコードで管理する（必須ではない）
- セキュリティ最低ライン:
  - TLS必須（本番 / ステージング）
  - パスワードはハッシュ化（WordPress 標準機能を利用）
  - 秘密情報は環境変数管理（DB パスワード等をコードに直書きしない）
- パフォーマンス目安（任意）:
  - 初期表示: 2〜3秒以内（ローカル開発環境を除く目安）

---

### 4.2 CI(自動テスト)/CD(デプロイ)
**MVP では未実装（将来機能として検討）**

将来的な実装案:
- プルリクエスト時に以下を自動実行:
  - ビルド（Gulp タスクの実行確認など）
  - ユニットテスト（必要に応じて PHP / JS / テーマ用のテストを追加）
  - 静的解析（PHP CodeSniffer / ESLint / Stylelint など、導入は decisions.md で決定）
- main マージ後:
  - staging へ自動デプロイ（手段は後で決定）
  - prod は手動承認を挟む

---

### 4.3 監視・ログ（最低限）
- エラーが起きたときに確認できるログを残す（PHP エラーログ、Web サーバログなど）
- 動作状況（アクセス数・エラー数・速度）を確認できること（本番での簡易モニタリングツール / サーバメトリクス）
- 動作確認用の URL（ヘルスチェック）を用意する（例: `/health` または WordPress トップページの疎通確認）

---

### 4.4 セキュリティ最低ライン
- 通信は必ず暗号化する（本番 / ステージング環境は HTTPS）
- パスワードは安全な方法で保存する（WordPress 標準のハッシュ機構を利用）
- 秘密情報はコードに直接書かない（`.env` や Docker シークレットなど）
- DB / API アクセスは必要最低限の権限だけを使う（DB ユーザ権限の最小化）

---

### 4.5 バックアップ・運用
- prod環境は定期的にバックアップする（DB と wp-content を対象）
- バックアップ頻度・保存期間・復元手順などの詳細は decisions.md に書く

---

### 4.6 パフォーマンス（任意）
- 最初の画面表示は 2 秒以内を目標とする（本番環境）
- 画像・CSS・JS の最適化（圧縮・結合 等）は将来機能または別途検討

## 6. 完成の定義（Definition of Done）
- README を見れば誰でもローカル起動できる（wp-env + Docker + Node + Gulp のセットアップ手順を記載）。
- MVP の主要フロー（ページ表示、テーマの基本動作、問い合わせ送信）が手動テストで確認されている。
- 開発環境（ローカル wp-env）で以下が動作確認できる:
  - トップページ・記事ページの表示
  - Sass コンパイル + ホットリロード
  - Contact Form 7 による問い合わせ送信
  - レスポンシブ表示（PC / スマホ）
- WordPress 管理画面からテーマが有効化でき、基本機能が動作する。
- インフラ構成が .wp-env.json として管理されている。
- 開発時の WordPress デバッグログが wp-content/logs/debug.log に出力される設定。

**将来的な完成条件（MVP では対象外）:**
- CI (自動テスト)がすべて成功している。
- staging / prod にデプロイ済みで URL にアクセス可能。
- 本番環境でのログ・メトリクス・ヘルスチェック確認。
